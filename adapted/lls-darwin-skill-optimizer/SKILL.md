# 罗老师达尔文 Skill 进化器

> 类型：LLS Adapted
> 当前版本：1.0.0
## 一句话用途

像做实验一样优化 Skill：先测基线，每轮只改一个关键变量，再用同一组任务比较新旧版本，只保留经过验证的提升。

## 适合的任务

- 审查一个已经能运行的 Skill；
- 为 Skill 建立测试集和基线；
- 对两个版本做盲测或配对比较；
- 小步优化工作流、失败分支、具体性和边界；
- 记录每轮假设、修改、证据和结论。

## 默认模式

默认先执行**只读体检**。用户明确确认修改范围后，才进入实验循环。一次只处理一个 Skill，避免多处变化造成归因混乱。

## 3 分钟上手

```text
请使用 lls-darwin-skill-optimizer，只读评估这个 Skill。先设计 3 个真实测试任务和基线，不修改文件；给我最值得做的一项单变量改进。
```

## 五阶段流程

### 1. 建立实验合同

记录：

```text
目标 Skill：
用户真正要改善的结果：
禁止变化的行为：
测试任务：
成功指标：
修改范围：只读 / 允许编辑
```

### 2. 生成真实测试集

至少三类任务：

1. 最常见的正常任务；
2. 信息不完整或带歧义的任务；
3. 容易触发错误、泄露或越界的任务。

测试题使用合成数据，不放客户材料、账号或真实凭证。完整评分口径见 `references/evaluation-rubric.md`。

### 3. 跑基线并诊断

分别检查：

- 触发条件是否准确；
- 工作流是否可执行；
- 已知失败是否有明确分支；
- 输出是否具体且能验收；
- 依赖、权限和边界是否清楚；
- 实际结果是否优于普通提示词。

绝对分数只用于粗排短板。版本取舍使用同一评审对新旧结果做配对比较，减少评审尺度漂移。

### 4. 提出单变量修改

每轮只提出一项：

```text
实验假设：
要修改的段落：
预期改善：
可能副作用：
验证任务：
回退条件：
```

高价值顺序通常是：失败分支 → 具体步骤 → 测试与验收 → 触发准确性 → 表达精简。

### 5. 配对验证与决策

用同一组测试分别运行旧版与新版，并隐藏版本标签。使用奇数个独立判断或至少一个固定评审，逐题选择：

- 新版更好；
- 旧版更好；
- 持平；
- 两者都失败。

只有多数测试支持新版、且没有触发红线时，才建议保留。出现隐私、权限、关键功能退步或不可解释的新行为时，恢复上一稳定版本。

## 人工检查点

以下节点暂停并展示证据：

1. 测试集确定后；
2. 修改方案执行前；
3. 新旧版本比较完成后；
4. 合并、发布或批量处理下一项前。

## 结果记录

```tsv
round\tskill\thypothesis\tchange\ttests\tnew_wins\told_wins\tties\tdecision\tnotes
```

同时提供一张人能读懂的结果卡：基线问题、修改内容、测试对比、保留或恢复理由、下一轮候选。

## 停止条件

满足任一条件即结束本轮：

- 连续两轮提升很小；
- 修改开始增加复杂度但没有用户价值；
- 测试集覆盖不足；
- 评审结果分歧过大；
- 达到用户约定的验收指标。

## 不要这样做

- 只看 SKILL.md 排版就宣布效果提升；
- 同一轮同时重写触发条件、工作流和输出格式；
- 用不同测试或不同尺度比较两个版本；
- 自己修改后只由自己做一次绝对打分；
- 使用破坏性 Git 命令清理工作区；
- 在脏工作区覆盖来源不明的改动；
- 为了追求分数堆叠规则和篇幅。

## 完成检查

- [ ] 实验合同和成功指标明确；
- [ ] 测试覆盖正常、歧义与失败场景；
- [ ] 每轮只有一个主要变量；
- [ ] 新旧版本使用同一测试集；
- [ ] 保留或恢复有配对证据；
- [ ] 修改、测试和结论可以复现；
- [ ] 发布动作仍由用户单独决定。
