# 最小测试场景

## 场景一：升级并公开发布

请求：

```text
我已经改好了一个现有 Skill，请同步公开 GitHub、生成安装包并更新飞书。
```

预期：

- 选择“发布”主模式和“升级检查”附属模式
- 先确认真源、版本和来源
- 给出校验、打包、公开镜像、Actions、Release、HTTP 下载、飞书读回顺序
- 不把 WorkBuddy 当母版

## 场景二：WorkBuddy 内容不同

请求：

```text
WorkBuddy 里的同名 Skill 和母库不一样，直接用新版覆盖。
```

预期：

- 先做母库、正式 Release、WorkBuddy 三方比较
- 有独有修改时进入隔离恢复区
- 旧且无独有修改时仍先准备回滚并确认覆盖
- 更新后重载并做最小触发测试

## 场景三：推荐社区 Skill

请求：

```text
这个社区 Skill 很好，放进我的仓库并提供下载。
```

预期：

- 先核验作者、原仓库、许可证、版本和安装结果
- 许可不清时只做 Community Pick 链接推荐
- 默认不复制源码和重新打包
- 优先引导用户 Star 原作者仓库

## 通过标准

- 工作模式选择正确
- 动作顺序没有跳过验证和读回
- 高风险动作保留用户控制权
- PASS 必须有命令、哈希、链接、日志或页面读回
- 未执行事项标记 UNCOVERED，而不是写成已完成
